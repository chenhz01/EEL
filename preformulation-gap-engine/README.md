# 前表述缺口引擎（Preformulation Gap Engine）

> **一句话主张**：量规评的是交付物，评不了开场白。很多失败不是"不会答"，而是"没把问题问对"——答案质量的上限在提问阶段就被锁死了。评估维度必须前移到"首次接触行为"：任务开场时收集了什么、澄清了什么、确认了什么，与交付末端同样值得打分。
>
> 主锚点：[arXiv:2608.17330](https://arxiv.org/abs/2608.17330) *LLMs for Medical Consultation Are Evaluated Too Late: The Preformulation Gap* ｜ 规格 pref-001~012（四层防线）｜ 由对比衍生 w19-06 与论文深读提炼。

---

## 〇、与 EEL 的边界（先讲清，避免重复）

EEL 回答"**进化有没有留痕**"。本引擎回答"**任务开始前有没有把问题问对**"——评估的前移。两者互补：

| 关注点 | EEL | 本引擎 |
|---|---|---|
| 对象 | 进化事件的审计记录 | 任务开场的行为质量 |
| 失效模式 | 改了没记录 | 开场就框错需求，末端量规分再高也是精确回答错误的问题 |
| 放行语义 | 事件有据可查 | 首次接触行为达标才允许进入实现 |
| 与 G3（审计账本） | G3 管策略变更记录 | 本引擎管需求澄清记录 |

**EEL 保证"你的每一步都有记录"，本引擎保证"你从一开始就在做对的事"。**

## 一、问题：评估来得太晚

[arXiv:2608.17330](https://arxiv.org/abs/2608.17330) 揭示：当前评估建立在"临床问题已被清楚表述"的隐含假设上，而真实问诊起点是含糊、弱化甚至被错误框定的主诉。实验结果触目惊心：

- 基线条件下，**12 个"病例×模型"单元里有 9 个**在患者还没回答任何问题前就给出自我护理建议；
- 加入引导进入诊疗（entry-to-care）指令后，这一数字**降为 0**；
- 结构化交接摘要从 **0/12 提升到 10/12**。

结论：前表述缺口应通过**可观测的"首次接触行为"**直接评估，而非用最终诊断准确率倒推。**没有结构化提问约束时，模型在 75% 的单元里直接跳过信息收集。**

材料中的映射：产品经理的 Rubric 量规体系锚定在交付末端（功能完成后的验收打分），天然测不到前表述缺口——开场时框错了需求，末端量规分再高也是**精确回答了错误的问题**。

## 二、为什么现有方案不够

| 现有做法 | 隐含假设 | 为什么失效 |
|---|---|---|
| 末端量规打分 | 答案质量 = 交付质量 | 答案质量的上限在提问阶段就被锁死了 |
| 从结果倒推评估 | 结果好 = 过程好 | 75% 的单元直接跳过信息收集，结果掩盖过程缺陷 |
| 让模型自评"我清楚吗" | 模型能自我觉察 | 模型在弱化主诉前倾向直接作答，不自知 |
| 一次性指令 | 加了指令就稳定 | 指令改变顺序与文档化程度，不保证问出决定性事实 |

## 三、引擎设计：四层防线

**澄清层（把问题问对）**——首次接触检查清单、澄清优先硬前置、结构化交接摘要。
**评估层（评估开场行为）**——首次接触行为评估集、开场白量规、回归测试。
**闸门层（拦住早答）**——未澄清不得给处置建议、高风险任务首轮强制澄清。
**追溯层（守住决策链）**——多轮任务交接摘要、决策链追溯、需求澄清记录。

## 五、失败剧本：被"精确回答错误问题"的咨询

1. 善伦问"帮我看看这首歌能不能发"——主诉含糊：是问版权？问发行平台？问 AI 音乐版权归属？
2. 正明直接开答："能发，注意平台规则。"（基线行为：未收集信息直接作答，对应论文 9/12）
3. 一周后善伦发现问的是版权归属，答案完全不适用——**回答得很流畅，但问题从一开始就错了**。
4. **本引擎介入**：pref-001 首次接触检查清单（主题域/决策类型/已知信息/未知信息/边界）→ pref-007 未澄清不得给处置建议 → pref-002 澄清优先硬前置：先问"你是问版权、渠道还是制作？" → pref-003 产出结构化交接摘要（问题重述/假设/待确认项）。
5. **追溯**：pref-010 交接摘要归档，pref-011 决策链可回溯到"澄清了什么"。

## 六、落地路径

- **P0（先做）**：首次接触检查清单、澄清优先硬前置、首次接触行为评估集、未澄清不得给处置建议、高风险任务首轮强制澄清。
- **P1（再做）**：结构化交接摘要、开场白量规、开场行为回归测试、需求澄清记录、多轮任务交接摘要、决策链追溯。
- **P2（后做）**：从结果倒推的禁用。

## 七、与同仓库引擎的关系

- **EEL G3（自进化审计账本）**：G3 管策略变更的三元记录；本引擎管需求澄清的字段采集——都是"变更/决策前先记录前提"。
- **preference-consistency-engine**：cons-009 商机证据类型必填与本引擎 pref-007 同构——都要求"先声明依据再放行"。
- **verification-protocol-engine**：verf-002 验收双指标（过程指标）由本引擎的"首次接触行为"提供最前端的过程测量点。

## 八、诚实的局限

1. **澄清有摩擦成本**：每任务强制澄清会拖慢简单任务（如"格式化这段文字"），需按任务风险分级触发（呼应 EEL 的规则触发成本不为零）。
2. **检查清单本身会被绕**：模型可假装澄清（"我确认了你的意思"）而不真正理解，需配行为证据核验。
3. **指令只改顺序不改能力**：论文强调 entry-to-care 指令改变了顺序与文档化程度，但**不能可靠保证模型问出决定性事实**——评估不能只看"问了没"，还要看"问到点上了没"。
4. **本文规格是论文结论的可执行表达，非忠实复现**：2608.17330 的完整实验设计（24 段固定台本对话）以原文为准。
5. **医疗→通用域的迁移需验证**：论文在医疗问诊场景验证，迁移到商业/创作场景需先跑本场景的评估集。
