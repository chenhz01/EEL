# EEL 双环存储设计（热 / 冷）

> 状态：设计文档 ｜ 版本 v0.1 ｜ 2026-08-20

---

## 1. 为什么需要双环

哈希链解决"篡改可发现"，但没有解决"链本身还存在"。本地 localStorage 的单点存储有三个致命弱点：

1. **单点失效**：浏览器清缓存、换设备、系统重装 → 链丢失，审计归零；
2. **单点篡改**：攻击者直接改 localStorage 再重算整链哈希 → 链"完整但全假"（需要外部锚定才能发现）；
3. **无仲裁**：链只有一份，无法与第三方对账。

双环存储 = **热环（高频校验，低延迟）+ 冷环（历史归档，高冗余）** 的组合。

## 2. 架构

```
┌────────────────────────────────────────────────────────────┐
│                      EEL 节点（Agent 侧）                     │
│                                                            │
│  写入事件 → 六锁校验 → 哈希上链 → ①写热环 ②异步归档冷环         │
└──────────────┬──────────────────────────────┬─────────────┘
               │                              │
        ┌──────▼───────┐              ┌───────▼──────┐
        │   热环 HOT    │              │   冷环 COLD   │
        │  (近期验证)    │              │  (历史归档)    │
        │              │              │              │
        │ · 内存 +      │              │ · 本地磁盘    │
        │   localStorage│              │   JSONL 追加  │
        │ · 保留最近 N 块│              │ · 可选：      │
        │   (如 100)    │              │   IPFS 固定   │
        │ · 秒级校验    │              │   / Git 提交  │
        │ · 主动校验    │              │ · 月度完整性  │
        │   每次加载     │              │   快照校验    │
        └──────────────┘              └──────────────┘
```

## 3. 双环职责划分

| 维度 | 热环 HOT | 冷环 COLD |
|---|---|---|
| 数据范围 | 最近 N 块（滑动窗口） | 全量历史（append-only 追加文件） |
| 载体 | 内存 + localStorage | 磁盘 JSONL / IPFS / Git |
| 校验频率 | 每次加载 + 每次写入后 | 月度 + 导出时全量 |
| 延迟要求 | 毫秒级 | 秒级即可 |
| 冗余度 | 单副本（本机） | ≥2 副本（本机 + 远端） |
| 用途 | 实时护栏校验 | 长期审计、第三方对账、灾难恢复 |

## 4. 关键机制

### 4.1 滑动窗口（热环）

- 热环只保留最近 `HOT_WINDOW=100` 块 + 窗口首块的 `prev_hash` 锚点；
- 窗口外的块只保留"哈希摘要引用"，完整内容交给冷环；
- 校验热环 = 校验窗口内链 + 窗口首块 prev_hash 是否命中冷环锚点。

### 4.2 冷环归档格式（JSONL）

```
{"index":0,"prev_hash":"sha256:GENESIS","ts":…,"type":"…","summary":"…","guardMeta":{…},"hash":"…"}
{"index":1,"prev_hash":"sha256:…","ts":…,"type":"…","summary":"…","guardMeta":{…},"hash":"…"}
```

- 一行一块，**只追加**，永不改写；
- 每 1000 块写入一个 `checkpoint.json`：`{"block_index":1000,"chain_head_hash":"…","ts":…}`，用于快速定位与部分校验。

### 4.3 外部锚定（对抗"全假链"）

热环 + 冷环都在本机 → 攻击者可同时篡改。**外部锚定**是唯一防线：

| 锚定方式 | 强度 | 成本 |
|---|---|---|
| 每周把链尾哈希发布到 GitHub commit | 中（依赖账号安全） | 极低 |
| 把链尾哈希写入区块链（存证服务） | 高 | 低（按次计费） |
| 第三方审计节点定期签名链尾 | 高 | 中 |
| 多节点互相广播链尾哈希（P2P） | 中高 | 中 |

最小可行锚定：**每周一次 git commit 记录 `chain_head_hash`**（仓库里放 `anchors/` 目录）。

### 4.4 灾难恢复

1. 本机全丢 → 从冷环远端副本恢复 JSONL → `tools/eel_verify.py` 全量校验 → 重建热环窗口；
2. 部分块损坏 → 校验定位到断点 → 用远端副本替换损坏块 → 重新校验；
3. 全假链嫌疑 → 比对外部锚点（git/链上）的链尾哈希 → 不一致则判定整链不可信。

## 5. 实现建议（分阶段）

- **P0**：localStorage 热环 + 磁盘 JSONL 冷环 + `tools/eel_verify.py` 支持 JSONL 校验；
- **P1**：checkpoint 机制 + 每周 git 锚定（`anchors/YYYY-WW.json`）；
- **P2**：IPFS 固定冷环副本 + 第三方审计节点 API。

## 6. 诚实局限

1. 外部锚定只在"锚定时刻之后"有效——锚定前的历史仍依赖本机冷环副本；
2. git 锚定的强度 = GitHub 账号安全强度，不能当作绝对不可篡改；
3. 冷环冗余增加运维成本，单用户场景可先只做本机双副本；
4. 本设计未覆盖密钥管理（签名的私钥如何保管），生产部署需另立密钥策略。
