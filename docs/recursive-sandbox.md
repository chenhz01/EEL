# 递归改进沙盒设计（进化控制层）

> 状态：设计文档 ｜ 版本 v0.1 ｜ 2026-08-20

---

## 1. 问题：递归改进的"不可逆突变"

自进化 AI 改自己的代码，最大风险不是"改错了"，而是：

1. **突变不可逆**：直接改生产代码，错了没有退路（versioned-workspace-engine 已论证"错误可逆"的价值）；
2. **连锁污染**：一次改动扩散进记忆/技能库，回滚参数不够（capability-collapse-defense clps-009）；
3. **自改进自证**：AI 自己改、自己验，评估层可写 → 奖励规格被篡改（EEL G2 + clps-005）。

沙盒 = 让"改自己"这件事变得**可试验、可回滚、可隔离**。

## 2. 代码沙盒与分叉隔离区

### 2.1 三层沙盒

```
┌─────────────────────────────────────────────┐
│ 生产区（PRODUCTION）· 只读基准 + 受控写入      │
│   仅接受：人类签名 + 共识确认的合并             │
├─────────────────────────────────────────────┤
│ 暂存区（STAGING）· 分叉验证                   │
│   AI 改进在此分叉、测试、比对，不触碰生产       │
├─────────────────────────────────────────────┤
│ 影子区（SHADOW）· 完全隔离                    │
│   高风险改进在此模拟运行，产出只读报告          │
└─────────────────────────────────────────────┘
```

### 2.2 分叉-合并规则

- 每次改进 = 在 `STAGING` 分叉（fork），带版本号与父版本引用；
- 验证通过（六锁 + 外部基准）→ 提交合并请求 → 人类或共识批准 → 合并进 `PRODUCTION`；
- 合并前强制生成**最小可审计变更**（clps-007）：diff 可逐行审查；
- 任何失败 → 从版本快照回滚（versioned-workspace-engine）。

### 2.3 影子区用途

- 高风险改进（改评估层、改价值锚点、改权限系统）**必须**先进影子区；
- 影子区运行 = 真实输入回放 + 输出隔离，绝不外发；
- 影子区产出《风险预演报告》供人类决策。

## 3. 改进提议的模拟推演

### 3.1 世界模型推演

- 对每个改进提议，用世界模型（World Model）在虚拟环境推演：
  - **短程**：该改动在 1-10 轮内的能力变化；
  - **长程**：是否会触发价值漂移、能力塌缩（clps-001 双曲线分叉检测）；
  - **反事实**：若任务顺序不同，结果是否稳定（clps-002 任务顺序方差基线）。
- 输出：动态风险预测评估报告（带时间维度）。

### 3.2 推演不通过的处理

| 推演结果 | 处理 |
|---|---|
| 长程风险低 | 允许进 STAGING |
| 长程风险中 | 限影子区，加护栏 |
| 长程风险高 / 触发分叉预警 | 拒绝 + 生成护栏（clps-010 回滚提炼护栏） |

## 4. 安全锁死密码（保护"元规则"）

### 4.1 什么是锁死密码

AI 可以改自己的业务代码，但**绝不允许改"允许改自己"的规则本身**——否则一切审计都是笑话（自改进的元规则必须人类持有）。

### 4.2 三层写保护

| 层级 | 内容 | 保护方式 |
|---|---|---|
| 物理级 | 部署环境只读挂载（容器/文件系统） | 基础设施 |
| 算法级 | 核心元规则硬编码 + 哈希校验 | 代码层面 |
| 治理级 | 多方托管签名（人类多把私钥） | 组织层面 |

### 4.3 元规则清单（不可改）

1. EEL 协议 v1.0 本身（protocol-v1.0.md）；
2. 六锁定义与阈值；
3. 价值内核 L0 宪法层；
4. 沙盒分层规则；
5. 谁有权限改"上述清单"——人类签名。

## 5. 落地路径

- **P0**：STAGING 分叉 + 合并审批 + 最小可审计变更；
- **P1**：影子区 + 世界模型推演（先做规则型推演，再做学习型）；
- **P2**：多方托管签名 + 元规则不可变校验。

## 6. 诚实局限

1. 世界模型推演的能力本身有限——模型预测不了未知风险，推演通过≠绝对安全；
2. 沙盒隔离增加工程复杂度，小团队需权衡（P0 先行即为此）；
3. 元规则"不可改"在实践中有灰色地带（如安全漏洞修复需要改元规则），需定义例外流程；
4. 本设计为可落地表达，具体技术选型以生产环境为准。
